# グループチャット

作業ブランチ `codex/group-chat` で実装。mainへの統合・本番マイグレーション・本番公開は未実施です。先にローカルで2ユーザーの動作を確認します。

## 確定仕様

- 管理者が設定した既存グループごとに1部屋。部屋IDはグループIDと分け、将来の複数部屋へ拡張できるようにします。利用者による部屋作成はありません。
- 所属メンバーだけが閲覧・送信可能。管理者も未所属の部屋にはアクセスできません。複数所属時は部屋を切り替えます。
- 新規参加者も参加前の履歴を閲覧できます。所属を外すと次のAPIから拒否し、画面は次回更新時に履歴を消します。再参加後は過去履歴を再び閲覧できます。
- 本文は最大2,000 UTF-16コード単位（画面のカウンターと同じ）。改行・Unicode絵文字に対応し、HTMLは文字として表示します。添付ファイル・画像・絵文字リアクションはありません。
- 投稿者は自分の本文を編集・削除可能。管理者本人は所属する部屋の他人の投稿も削除できます。他人の編集はできません。
- 編集済み表示、削除済みの枠を残します。削除操作では本文を空にして復元不能にします。自動の履歴削除はありません。
- チャット画面の表示中だけ5秒間隔で差分取得。再表示・フォーカス復帰時は即時取得します。通信エラー時は履歴を維持し、エラーを表示して再試行します。
- 初回は新しい50件、過去分はボタンで50件ずつ追加。差分は編集・削除を含み、201件を超えた分はカーソルで続けて読みます。
- 同一の再送IDは同じ投稿を返し、二重保存を防ぎます。連続する新規投稿は1人あたり1秒以上空けます。編集・削除は版番号で競合を検出します。
- 部屋ごとの未読件数を表示します。画面が表示中で履歴の末尾まで到達したときに既読を保存します。過去履歴を読んでいる最中・通知だけの受信では既読を進めません。
- 各投稿の「既読」から読んだ人の表示名を確認できます。現在のグループ参加者を対象とし、投稿者は人数から除きます。

## 通知

- Web標準のPush API・Service Worker・VAPIDを利用します。外部の認証・通知SaaSやDurable Objectsは使いません。
- 暗号化とVAPID署名に `@block65/webcrypto-web-push` を使用します。暗号処理を独自実装せず、WorkersのWeb Cryptoで動かすための依存です。
- 初期状態は無効。各端末で「通知を有効にする」を押してブラウザーへ許可します。ユーザーごとに最大5端末を登録できます。
- 部屋ごとのミュートはD1に保存して端末間で共有します。端末の通知解除はその端末のみ。ログアウト時に解除し、セッション失効後の配信も止めます。
- タイトルは送信者名、本文はメッセージ先頭600 UTF-16コード単位。グループ名を載せません。自分の送信、ミュート中、同じ部屋を表示中の端末には通知しません。
- 通知を押すと `/tools/chat?room=<room-id>` を開きます。グループ変更、セッション失効、別アカウントへの切替を配信時と受信時にも確認します。
- 一時的な送信失敗でもメッセージはD1へ保存済みです。通知ジョブもD1へ置き、1分間隔のCronで再試行します。1回最大3端末、1ジョブ最大10回とし、配信サービスへの接続は1端末6秒で打ち切ります。失敗・待ち行列・OSの都合により通知が数分遅れたり届かなかったりする場合があります。通知は到達保証・リアルタイム配信保証をしません。
- 404/410で失効した購読を解除します。送信記録で再試行時の重複を減らしますが、配信サービスの成功後にDB保存が失敗した場合など、厳密な一度限りの配送は保証しません。
- 受信時に本人確認できない場合は本文を表示しません。オフライン・Cookie制限・通知権限・省電力設定も届かない原因になります。再ログイン後は端末の通知を有効にし直してください。
- Service Workerは通知専用です。個人データやAPIをオフラインキャッシュしません。

## 対応端末とローカル確認

- Windows: 標準Pushに対応するChrome・Edge・Firefoxなど。OSとブラウザーの通知許可が必要です。
- Android: 対応ブラウザーでHTTPSサイトを開き、通知を許可します。ホーム画面への追加も可能です。
- iPhone/iPad: iOS/iPadOS 16.4以降で、HTTPSサイトを「ホーム画面に追加」し、追加したアプリ内で通知を許可します。通常のSafariタブでは同じ条件になりません。[WebKitの説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- PC自身の `http://127.0.0.1:5173` は開発用の安全なオリジンとして通知を試せます。スマートフォンからPCのLAN IPをHTTPで開くだけではPushを検証できません。実機通知は別D1・別Secretsを使う隔離HTTPSプレビューで確認します。

```sh
bun install --frozen-lockfile
bun run wrangler d1 migrations apply my-tools-web-db --local
bun scripts/createChatKeys.mjs --local
bun run dev --host 127.0.0.1 --port 5173
```

認証用の `.dev.vars` は既存のものを使用します。鍵作成後は開発サーバーを再起動します。通知の鍵は上書きしません。

管理者アカウントで一般ユーザーを2名作り、同じ確認用グループへ追加します。片方を通常ウィンドウ、もう片方を別ブラウザーまたはプライベートウィンドウで開いてください。同じブラウザープロファイルの複数タブはログインCookieを共有します。

1. Aが投稿し、Bの画面へ約5秒以内で届くこと。
2. Bが末尾を表示し、Aの「既読」にBの名前が出ること。
3. Aが編集・削除し、Bへ反映すること。他人の投稿は編集できないこと。
4. 過去履歴、別の部屋への切替、スマートフォン幅、キーボードでの操作を確認。
5. Aが通知を有効にし、チャットを非表示にしてBが投稿。送信者名・本文だけの通知から部屋へ戻れること。
6. ミュート・解除・ログアウト、所属解除後は新規の受信を止めること。

テスト用のパスワード・Cookie・ローカルDBはGitへ追加しません。

## 構成とAPI

画面: `src/tools/chat/`、共有契約: `shared/chat.ts`、API/DB: `worker/tools/chat/`。入口は `worker/http/privateRoutes.ts` でセッション確認後に接続します。すべて同一オリジン・キャッシュ禁止です。

| API | 用途 |
| --- | --- |
| GET `/api/chat/rooms` | 所属する部屋・未読数・本人・通知公開鍵 |
| GET `/api/chat/rooms/:roomId/messages` | 初回50件。`before`で過去、`since`で差分 |
| POST 同上 | `body` と `clientId` による投稿 |
| PUT/DELETE `/api/chat/rooms/:roomId/messages/:id` | 版番号付き編集・削除 |
| POST `/api/chat/rooms/:roomId/read` | 表示済みの最終投稿ID |
| PUT `/api/chat/rooms/:roomId/mute` | 本人の部屋のミュート |
| GET/POST/DELETE `/api/chat/device` | 現セッションの購読確認・登録・解除 |
| POST `/api/chat/presence` | 非表示・部屋切替時の通知抑制解除 |

`0006_chat.sql` は新規テーブル・索引の追加だけです。既存認証・カレンダー・Todoのデータを変更しません。部屋・履歴・既読・ミュート・端末購読・通知ジョブ・送信記録を分けています。グループ削除時は関連するチャットも外部キーのCASCADEで削除されるため、運用中のグループ削除は内容を確認して行ってください。

## 費用と公開前の確認

Workers/D1のFreeプラン内での利用を前提にし、有料サービス・課金契約の作成は行いません。ただし、このリポジトリーからアカウントの現在の契約プランや残量を固定することはできません。公開前にCloudflareダッシュボードの契約・使用量を確認してください。

全員が1時間チャットを開いた場合、10人×720回=約7,200回のメッセージ取得です。このほかに認証・部屋一覧・既読・Cronの要求とD1の読み書きがあります。履歴が増えると未読件数の集計対象も増えるため、人数だけで無料枠内を保証しません。制限到達時は更新や通知に失敗し得ます。

[Workersの制限](https://developers.cloudflare.com/workers/platform/limits/)と[D1の料金](https://developers.cloudflare.com/d1/platform/pricing/)を確認し、無料枠の利用状況を監視します。有料プランへ自動変更するコードはありません。

ローカルの共同確認が完了するまでmainへマージしません。本番公開時には別途、次を実施します。

1. 対象DB・既存データへの影響を確認し、`0006_chat.sql` を本番へ適用してから更新を公開する（Workerのデプロイだけでは反映されません）。
2. `bun scripts/createChatKeys.mjs --production` で本番用の別鍵をGit除外先へ生成する。
3. `VAPID_PUBLIC_KEY`、`VAPID_PRIVATE_KEY`、`VAPID_SUBJECT` の3つを `bun run wrangler secret put <名前>` で設定する。秘密鍵を画面・コミット・チャットへ貼らない。
4. 検証後にmainへ統合し、既存のGitHub連携で公開する。Cron `* * * * *` の有効化も確認する。
5. 実機のWeb Push到着・クリック・ミュート・ログアウトと、WorkersのCPU使用量を確認する。今回のローカル検証だけで本番の通知到着を検証済みとしない。
